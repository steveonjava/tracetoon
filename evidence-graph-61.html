What Tracetoon is

Tracetoon is an open-source tool that writes better pull-request descriptions from the work an AI coding agent already did. Agents such as Claude Code, Codex, Copilot and Cursor keep session logs on disk: the user's requests, plans, decisions, file edits and the commands they ran. A PR description written from the diff alone loses most of that. It can't say why the change was made, what was tried first, or which tests actually ran on the final code. Tracetoon runs as an agent skill, and when an agent is about to open a PR it takes over in five steps:

  1. Finds the matching sessions by matching agent edits to lines in the diff, and asks when a session is ambiguous.
  2. Builds a redacted evidence set of prompts, plans, edits, runs and commits, with private paths and secrets removed.
  3. Writes the description from that evidence and checks it: every factual sentence must trace back to evidence, and the Validation section is generated from recorded test and build runs, not typed by the model.
  4. Draws an optional comic of the change, left out where a repo's rules forbid images or when you turn comics off.
  5. Creates the PR after review, then reports the link, whether a comic is included and any sessions it left out.

This page compares two versions of its drafting step: the original multi-agent workflow and the version built on an evidence graph.

How quality is judged

Each of the 61 PRs is a real change with the original agent session logs that produced it. Every description is judged against an expert-reviewed fact sheet, by two judges, in both orders.

The fact sheet

ListWhat it holdsItems per caseScored as
Claims (C1…)Facts about the change a good description should convey: new behaviors, changed defaults, tests added.4–16Claim coverage
Context (X1…)What a reviewer would want beyond the code: why the work started, what the user asked for, what was found along the way.2–6Context coverage
Uncertainties (U1…)What the evidence does not establish, such as a path never run live. A good description doesn't overclaim these.2–7Uncertainties respected
Traps (T1…)Plausible but wrong statements a writer might make, such as calling an existing function new.4–8Traps hit (penalty)

Sheets were drafted from the diff and logs, then reviewed by a six-model expert panel (three Claude Opus 5.5, three GPT-6.1 Sol); disputes were settled by mirrored debates judged by Fable 5.1 and GPT-6 Astra, with Fable deciding splits.

Pairwise judging, both orders, two judges

A judge sees the fact sheet, the commits, the diff, the session evidence, any fresh validation runs, and two descriptions labeled A and B. It marks every checkable clause supported, contradicted, unsupported (broader than the evidence) or unverifiable, scores ten reviewer-usefulness items, and says which description a maintainer would rather receive, with accuracy first, then usefulness, then the reader's effort. Codex runs use GPT-6.1 Sol and GPT-6.1 Terra as judges; Claude Code runs use Opus 5.5 and Sonnet 5.5. Each judge reads every pair in both orders. A judge's pick counts only when it is the same in both orders. Our headline "both judges agree" record counts the comparisons where both judges made the same order-stable pick; anything else is a tie. That is why the counts are well below the 183 pairs per provider.

The ten rubric items

ItemWhat the judge checks
problemThe trigger, the old behavior and the new behavior are clear, and the old behavior matches the base code.
rationaleReasons for the approach are explicit and correctly attributed.
validationWhat was checked, and how, is stated; claims are bound to evidence and limits are honest.

Each item is scored 0 (missing or misleading), 1 (partial) or 2 (sufficient and accurate), or left null when it doesn't apply.

The composite score

The composite rolls each judgment into one 0–100 number per draft, averaged over its judgments:

composite = 35·claims + 15·context + 15·uncertainties + 35·rubric − 15·errors − 7·unsupported − 10·traps

Coverage terms are fractions of the fact sheet (0–1). Rubric is the mean item score divided by 2. Errors, unsupported claims and traps are counts per judgment, so a single contradicted claim costs 15 points. The head-to-head record and the composite are reported separately because they can disagree: the composite rewards coverage, while the head-to-head reflects which draft a maintainer would rather get. Factual errors are also checked by experts: every error a judge flagged was re-checked against the evidence by Fable 5.1 and GPT-6 Astra (434 flags, none left unresolved).

Where the quality gain comes from

The composite difference splits into its terms. On Codex, most of the gain is key-fact coverage (+3.5) and rubric (+0.8), with smaller gains from context (+0.1); more factual errors (−1.0), more traps hit (−0.1) take part of it back. On Claude Code, most of the gain is rubric (+3.5) and fewer factual errors (+2.3), with smaller gains from context (+0.7); fewer respected uncertainties (−1.5), lower key-fact coverage (−1.4), more traps hit (−0.1) take part of it back.

Where the graph is weaker

  • Codex factual errors. Judges flagged more errors in Codex graph drafts (0.17 vs 0.10 per judgment), and after expert checking 61 of 81 flags held against 30 of 47 for the original: 0.33 vs 0.16 confirmed errors per draft, a difference of +0.17 [0.00, +0.36]. What drives it.
  • Claude Code uncertainties. Claude graph drafts respected fewer of the fact sheets' open uncertainties (57% vs 66%), even though expert-confirmed errors fell (0.47 vs 0.84 per draft).
  • Claude Code key facts. Claude Code graph drafts conveyed slightly fewer key facts (73% vs 77%), within our 5-point coverage margin.
  • Rubric items that got worse: Codex economy −0.66, scope −0.07, orientation −0.06; Claude Code consequences −0.22, scope −0.17, orientation −0.16, links −0.12.

The cost story is about where the expensive model spends its tokens. Without the graph, the expensive model reads source code to check its own claims, and on Codex each forked role re-reads the parent's history (2.65 subagent threads per PR on average). With the graph, that structural work is done once, deterministically, and building the brief costs no tokens. What's left is writing, plus a cheap model checking a short packet: reviews cost about $0.06 per PR on Claude Code (Haiku) and $0.008 on Codex (Luna). The writer also writes less: 7K output tokens per PR on Sonnet instead of 20K, and 3K instead of 10K on Terra.

Versus drafting the PR in the main session

Why not have the agent that did the work write the PR before it stops? It carries the whole session's context, so every model call re-reads hundreds of thousands of tokens. Prompt caching makes those re-reads cheaper but not free, and a PR still adds new tokens: the diff and git output it reads, and the description it writes. We estimate this rather than measure it, with the method of the earlier report:

  • 5 model calls to write a PR in the session: look at the diff and log, draft, open it.
  • Context per call: the end-of-session context size, measured from each case's original session log (Claude Code: input plus cache tokens of the last assistant message; Codex: the last token count). The average over the 61 PRs is about 408K tokens (range 132K–919K).
  • New tokens: about 10K of new input (diff and command output) and about 2K of output (commands and the PR body).
  • Cached: all 5 calls read the context from cache. Not cached: the cache has expired, so the first call writes the whole context to cache and the next 4 read it.
  • List prices: Sonnet $3/M input, $3.75/M cache write, $0.30/M cache read, $15/M output; Terra $1/M input, $0.05/M cached input, $5/M output. Any long-context surcharge is not included.

Tracetoon without a graph

The original workflow was already a careful multi-agent design. It reads the session logs through a digest and coordinates separate roles so that no agent checks its own work.

Roles

  • Coordinator: the host agent. Runs the CLI steps and usually drafts.
  • Researcher (subagent): collects repository guidance, contributing rules and AI policy.
  • Drafter (subagent, or the coordinator): writes the description from the digest, the patch and evidence lookups.
  • Independent reviewer (fresh subagent): checks every factual clause against the diff and source, looks for counter-evidence, lists omissions.

Steps

  1. status, doctor
  2. digest the sessions, choose the matching ones
  3. context and researcher phase
  4. draft from the digest
  5. comic (optional)
  6. render, then a fresh independent review
  7. up to two correction rounds, each with a re-render and a fresh review
  8. preview and publish

Cost in this run: $0.447 per PR on Codex (3.97M input tokens, mostly cached, and 10K output; 2.65 forked subagent threads per PR) and $0.654 on Claude Code (1.45M input, 20K output), all on the writer model. This run doesn't record cost per role. From the earlier 5-PR report: on Sonnet, the coordinator took about $0.29 per PR, reviewers about $0.35 over 1.4 review sessions, and the researcher about $0.05; on Codex the split was coordinator $0.11, drafter fork $0.09, reviewer fork $0.08 and researcher fork $0.04, because each forked role re-reads the parent's history.

The design is sound, and it produces accurate descriptions. Its cost comes from asking an expensive model to rediscover structure from text: which commit sentence maps to which hunk, which symbols are new, and why a change was made. Then a second instance does all of it again to check the first, at full price.

What the graph does

The graph moves that rediscovery out of the model and into a deterministic build step. One command, tracetoon prepare, reads the session logs and git, builds an embedded graph in Relate, adds search links from Relate's fulltext index, runs a fixed set of Cypher queries, and prints a compact evidence brief. No model is involved, so this step costs no tokens.

The graph

13 node types

Session · Prompt · Decision · Plan · Run · Receipt · Edit · File · Hunk · Commit · CommitClaim · Change · HeadRef

16 relationship types

SURVIVES_IN (an agent edit still present in the final diff) · TIED_TO (a search link from a commit sentence, request or plan to a hunk, with a score) · SAYS (commit → sentence) · EXPLAINED_BY · ASKED_BY · ASKED_BEFORE · EDITS · LATER_EDIT · INTRODUCED · IN_TURN · IN_SESSION · NEXT · OF · MADE · TOUCHES · HAS

The edge that does the most work is SURVIVES_IN, which connects an agent's edit in the logs to a hunk that's still in the final diff. From a hunk you can walk back to the prompt that asked for it and forward to the commit sentence that describes it.

Fewer roles, fewer steps

Without the graph

  1. digest, then a researcher subagent
  2. drafter reads the digest and patch, expands refs
  3. fresh reviewer re-reads the source
  4. up to two correction rounds, each with a fresh review
  5. render, publish

4 roles, all on the expensive model.

With the graph

  1. prepare: digest, graph, search links and brief in one deterministic step
  2. writer drafts from the brief, tagging every factual sentence with brief refs
  3. render --check: deterministic coverage and claim checks
  4. two cheap reviewers (general and completeness) at high effort, merged into one list
  5. one edit pass, render, publish

1 expensive role (the writer) plus 2 cheap reviewers. No researcher, no separate drafter, no re-review rounds, no forks.

Because every sentence carries brief refs, Tracetoon checks the draft without a model. It flags uncovered change units, commit sentences and tests; a sentence naming a file outside its cited change; "new" next to a name that already existed; "always" or "only" on code with a branch; results only a commit message claims; and a "housekeeping only" line when logic changed. Brief refs are stripped before the body is published.

Why Relate: an embedded graph database for agent systems

Relate is an embedded graph database written in Rust, and it is the engine this Tracetoon build runs on (pinned at v0.1.2-5, commit aa0f79e). Embedded means it runs inside the application process, with no server to install, start or connect to. Tracetoon ships Relate compiled to WebAssembly inside its CLI, so the same build runs on Linux, macOS and Windows, works offline, and builds a fresh graph for every PR. Agent tooling usually runs on a developer's machine, inside a sandbox or in CI, where a database server is a non-starter; Relate gives it a real graph model and Cypher with the footprint of a library.

The questions Tracetoon has to answer are relationship questions: which request led to this code, did a passing test run after the last edit, which commit sentence describes this hunk. Here is the core of the query that finds which user request produced a surviving piece of code, and which plans or decisions came with it:

MATCH (h:Hunk {id: $hunk})<-[:SURVIVES_IN]-(e:Edit)-[:IN_SESSION]->(:Session {band: 'included'})
OPTIONAL MATCH (e)-[:IN_TURN]->(p:Prompt)
OPTIONAL MATCH (x)-[:IN_TURN]->(p) WHERE x:Decision OR x:Plan
RETURN p.id AS prompt, p.text AS request, collect(DISTINCT x.id) AS plansAndDecisions

Some links have no structure to follow: a commit sentence about a script may share no symbol with the code it describes. For those, Tracetoon uses Relate's built-in fulltext index, which ranks hunks with BM25, and stores accepted hits as TIED_TO edges with a score:

CREATE FULLTEXT INDEX hunk_text FOR (h:Hunk) ON EACH [h.text]

MATCH (h:Hunk)
SEARCH h IN (FULLTEXT INDEX hunk_text FOR $text LIMIT 256) SCORE AS s
RETURN h.id AS hunk, s

Each of these would take a model thousands of tokens to reconstruct from raw text, and the result would vary from run to run. In Relate each is a deterministic query that costs no tokens, and because the brief comes from queries, every sentence in the PR can be traced back through a brief row to specific hunks and session lines.

How we got here

Each row is the graph workflow against Tracetoon's original workflow on the same model and harness. "Picks" are head-to-head wins–losses. The four tuning rounds ran on 25 of the 61 PRs with 2 replicates and one judge per provider (GPT-6.1 Terra for Codex, Sonnet 5.5 for Claude Code), so their picks count that judge's order-stable choices and aren't directly comparable with the two-judge rows. The two panel rows ran all 61 PRs once with both judges, against the same build's first replicate; their cost column is the saving per draft against candidate58, not against the original workflow.

The first 61-PR run showed the 5-PR result didn't carry over evenly: Codex still gained, Claude Code was level. Loss analyses traced most losses to the brief, not the model: motivation clipped, uncertainties deleted by an absence check, old behavior unstated, and passing runs hidden. The tuning rounds fixed those generically (no case names in any change); round 3 regressed and was reverted in round 4.

Round 4's build (candidate58) then ran on all 61 PRs with both judges: judges preferred it 71% of the time on Codex at 46% lower cost, and 80% on Claude Code at 31% lower cost. Two bug-fix builds followed for problems found in that run's drafts, such as Claude Code reviewers that ended the session before their review came back. candidate61 then combined a quality pass with a cost-focused pass. On a 61-case panel it cut cost, but Codex quality regressed (−7.4 ± 1.8 points against candidate58 on the same cases). The diagnosis traced the drop to the Validation section printing every open limit, several from unreliable generators. candidate62 keeps at most two reliable open points there, leaves the rest to the writer, and keeps the cost changes. On the same panel it matched candidate58's quality within noise (score gain −1.3 ± 1.4 on Codex, +1.4 ± 2.2 on Claude Code) at much lower cost. The results on this page come from candidate62's full 3-replicate run.

Method and caveats

Setup

  • 61 real pull requests from 12 repositories: Tracetoon (17), AI First CLI (10), prbench (9), Showtail (6), AI First content (4), VEX AIM agent (4), AI First website (3), VEX AIM workshop (3), VEX V5 serial (1), WinApps (2), AI First extension (1), Bazzite login (1).
  • Session logs: 33 from Claude Code, 28 from Codex.
  • Both workflows wrote every PR three times with the same model, prompt and sandbox; they differ only in the installed Tracetoon skill.
  • Writers: GPT-6.1 Terra (medium) in the Codex CLI and Claude Sonnet 5.5 (medium) in Claude Code 2.1.319. Reviewers in the graph workflow: Luna 6 and Haiku 5.5 at xhigh.
  • Two pre-registered judges per provider, both orders. Tracetoon build candidate62 (Tracetoon 8d9783f). Harness: prbench bench-v4 (writer side f4f7139), 61 cases x 3 replicates, pre-registered judge pairs, original-workflow drafts reused from the 2026-11-16 run (diagnostic purpose); the open prbench harness.

What to keep in mind

  • Tuned on part of the pool. After the first 61-PR run, the brief was tuned over four rounds on 25 of these cases (the 20 where it had lost most, plus 5 controls). On the 36 untouched cases the score difference is +3.4 (Codex) and +4.0 (Claude Code); on the 25 tuned cases +3.1 and +2.7. Picks on the untouched cases: 51–21 (Codex) and 42–11 (Claude Code).
  • Build chosen on a full-pool panel. candidate62 was chosen after a one-replicate panel on all 61 cases, and that panel's drafts are the first of this run's three replicates. The fixes behind it were generic (no case names), but the choice itself used this pool.
  • Single-judge tuning rounds. A harness bug passed only the last of the two judges during tuning, so rounds 1–4 were scored by one judge per provider. This final run is scored by both pre-registered judges.
  • Reused drafts. The original workflow's 183 drafts per provider come from the first 61-PR run; only the graph's drafts are new. Same models, harness, sandbox and judges.
  • No held-out set. All 61 cases form one pool used both to tune and to evaluate. An earlier sealed held-out split was used once; that run found errors (statements that no request or test was recorded) which the current build fixes. We then chose a larger single pool over repeated small held-out sets.

Accuracy: expert-confirmed factual errors

Every factual error a judge flagged was re-checked against the evidence by two expert models, and only confirmed errors count here. The rate is per graph or original draft, over all 183 drafts per provider, with a 95% interval over cases.

  • Codex: 0.33 confirmed factual errors per draft (61/183) with the graph vs 0.16 (30/183) for the original; difference +0.17 [0.00, +0.36]. This fails our strict non-inferiority gate, which needs the upper bound at or below +0.05.
  • Claude Code: 0.47 confirmed factual errors per draft (86/183) with the graph vs 0.84 (154/183) for the original; difference −0.37 [−0.58, −0.15]. This passes our strict non-inferiority gate (upper bound at or below +0.05).

What drives the Codex errors. About a third are in the Validation section, which Tracetoon generates rather than the writer. Two render bugs cause most of them. The line saying the session's last test run came before the final edits fires even when the edit and the test ran in one chained command, edit first. And checks are labelled as run on the submitted content when an earlier step had regenerated files in the tree they ran on. The rest are in the prose, mostly sentences broader than the code supports, such as calling every changed test fake-only or crediting the wrong function. These causes are known and being fixed.

Our own adoption gate. Before testing we fixed four criteria per provider: the score's lower 95% bound at least −2.5, expert-confirmed factual errors not worse by more than 0.05 per draft (the upper 95% bound of the difference), cost at most 0.8×, and key-fact coverage not lower by more than 0.05. Codex met 3 of 4 (missed: errors not worse by more than 0.05 per draft; confirmed errors 0.33 vs 0.16 per draft, difference interval up to +0.36). Claude Code met 4 of 4.

  • Judges disagree often. Agreement between the two judges was 69% (Cohen's κ 0.50) on Codex and 52% (κ 0.27) on Claude Code, which is why we lead with picks both judges agree on. The Codex judges include GPT-6.1 Terra, the same model as the Codex writer in both workflows; judges and writers are always from the same provider family.
  • Uncertainties and wall time on Claude Code. Claude graph drafts respected fewer uncertainties (57% vs 66%) and took about 1.6× as long per PR; on Codex wall time was 1.06×.
  • Sandbox validation. Writers ran tests in an offline sandbox. 31 of 61 cases' test suites pass there at the PR's final commit; the rest fail for host reasons or have no test command. Both workflows saw the same environment.
  • Compared with our earlier 5-PR report. That report measured +3.5 and 35% lower cost on Codex, and +5.2 and 41% on Claude Code, on 5 PRs from one repository. On 61 PRs the Codex saving grew (70%) and the Claude Code saving grew (43%); since then the graph workflow added fresh checks and a review pass to fix accuracy.
  • The example. The three-way drafts come from a separate one-replicate run on one case; the agent-alone cost is an estimate.
